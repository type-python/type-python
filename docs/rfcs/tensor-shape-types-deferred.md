# RFC: Deferred Tensor Shape Types

**Status:** research note; implementation deferred  
**Strategic source:** `docs/strategic-todo.md` Deferred Tensor Shape Types  
**Scope:** conservative direction for tensor/array shape typing, not a Core v1 feature

## Summary

Tensor shape typing is valuable for ML and data workloads, but it quickly becomes a dependent-type or
domain-specific language problem. TypePython should not add general shape algebra to Core. If tensor
support is revisited, it should begin as checker-neutral metadata and optional adapter/runtime
integration, not mandatory runtime assertions generated by the compiler.

## Survey snapshot

- **jaxtyping** uses annotations that combine array type, dtype, and symbolic shape strings, and can be
  paired with runtime checkers such as beartype. This is expressive, but the semantics are library DSL
  semantics rather than standard Python typing.
- **torchtyping** follows a similar runtime-aware pattern for PyTorch tensors, focusing on named tensor
  dimensions and runtime validation hooks.
- **beartype** can enforce rich annotations at runtime, which is useful at trust boundaries but changes
  runtime behavior and dependency expectations.
- **PyTorch** typing remains mostly nominal around `Tensor`; shape and dtype precision are largely
  outside standard `.pyi` expressiveness.
- **JAX** and its ecosystem use array annotations and shape-polymorphic concepts, but practical shape
  reasoning is tied to JAX tracing/compilation constraints.
- **NumPy typing** provides `numpy.typing` surfaces such as array-like and dtype-generic arrays, but
  portable static shape algebra remains intentionally limited.

## TypePython stance

TypePython should emit static metadata first:

```python
typealias ImageBatch = TensorShape["batch channels height width", dtype=float]
```

That metadata can feed hover, generated docs, or adapter-specific output. It should not imply that
Core assignability understands arbitrary symbolic arithmetic such as `N + 1`, broadcasting, or matrix
multiplication constraints.

## Runtime assertions

Runtime shape assertions should be opt-in at explicit boundaries, mirroring boundary validator policy.
The compiler may delegate to libraries such as jaxtyping/beartype when configured, but should not emit
mandatory assertion code for ordinary builds. Default emitted `.py` and `.pyi` should remain portable
and dependency-free.

## Non-goals

- No general dependent types in Core.
- No symbolic dimension arithmetic in v1.
- No implicit dependency on NumPy, PyTorch, JAX, jaxtyping, torchtyping, or beartype.
- No runtime shape checks unless the project explicitly opts in at a boundary.
